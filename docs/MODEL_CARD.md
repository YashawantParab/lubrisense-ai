# Model Card — Phase 11 ML Models

**This model is trained on synthetic industrial data and is not validated for production
machinery.** All values below are measured against a deliberately modest synthetic
reference dataset generated by the real simulator/edge/pipeline stack (see
`docs/ML_ARCHITECTURE.md` "Dataset generation") — not real plant telemetry, not real
failure history.

## Purpose

Two models produce Machine & Sensor Intelligence **evidence** (never a diagnosis or
maintenance decision, per CLAUDE.md's three-layer intelligence architecture):

1. **`LUBRICATION_ANOMALY_V1`** — unsupervised anomaly detection (Isolation Forest) over
   lubrication and machine-condition signals.
2. **`FAILURE_CLASSIFICATION_V1`** — supervised failure-pattern classification
   (`HistGradientBoostingClassifier`, benchmarked against a `LogisticRegression` baseline)
   over the same signals.

## Training data

Generated by `edge/scripts/generate_ml_training_data.py` driving real `SimulationEngine`
scenario runs through the real Phase 5/6 pipeline (simulator -> edge -> MQTT -> Kafka ->
TimescaleDB), then materialized into Phase 10 feature vectors
(`python -m app.features.materialize`). See `docs/results/model_evaluation.json` for the
exact measured counts from the run this model card describes.

- **Assets**: the flagship reference machine (`L1-7B43-M000`, 8 registered sensors — no
  FLOW/PUMP_RUNTIME/CYCLE_COMPLETION, the real heterogeneous-instrumentation case) plus one
  second, fully independent equipped machine (`L1-5F44-M020`) held out entirely for the
  asset-generalization test.
- **Scenarios**: HEALTHY (4 seeds) plus all 10 injectable simulator failure modes
  (`GRADUAL_RESTRICTION`, `SUDDEN_BLOCKAGE`, `LEAKAGE`, `PUMP_DEGRADATION`, `SENSOR_DRIFT`,
  `SENSOR_DROPOUT`, `INDEPENDENT_BEARING_FAULT`, `OVER_LUBRICATION`, `LOW_RESERVOIR`,
  `NETWORK_FAILURE`), most with two seeds/onset timings, plus one deliberate multi-fault run
  (`GRADUAL_RESTRICTION` + `INDEPENDENT_BEARING_FAULT` simultaneously).
- **Run duration**: 6 simulated hours per run, 60s ticks, compressed fault onset (~1.5
  simulated hours) so each run's window contains meaningful pre/post-onset signal at a
  duration practical on an i7/16GB development machine.
- **Non-overlapping time slots**: every run occupies a disjoint simulated time window on its
  machine (see `docs/ML_ARCHITECTURE.md`) — a correctness fix made during this phase; see
  the corresponding ADR in `TECHNICAL_DECISIONS.md`.

## Feature sets

`LUBRICATION_ANOMALY_V1` and `FAILURE_CLASSIFICATION_V1` (Phase 10 feature-catalog sets,
version `1.0.2`). Model-specific exclusions documented in `docs/ML_ARCHITECTURE.md`
"Model-specific feature selection" — most notably, Phase 9 rule-evidence features are
excluded from both models to keep ML evidence independent of the rules engine's own
detectors.

## Split strategy

Grouped by simulator run, time-ordered *within each label's own runs* (stratified): a
single global time-ordered cut across all 24 runs was tried first and, at this dataset's
scale, accidentally placed every run for two of the eight labels
(`INDEPENDENT_BEARING_ISSUE`, `UNKNOWN`) entirely outside TRAIN — making them structurally
unlearnable rather than merely hard to learn (confirmed by a first training pass at
classifier macro F1 ≈ 0.05). Splitting independently per label — a label's two runs go one
to TRAIN and one to TEST, its four runs go 60/20/20 — fixed this while still never crossing
a single run's samples across two splits and still never using row-random shuffling. The
second, fully independent asset's runs, the sole multi-fault-composition run, and the sole
connectivity-loss run are forced to TEST regardless of this stratification, since they are
each more valuable as an evaluation case than as TRAIN data. See
`docs/ML_ARCHITECTURE.md` "Splitting" and `ml_service.datasets.splitting.assign_stratified_run_splits`.
No sample from one run ever crosses a split boundary (`verify_no_run_crosses_splits`,
tested).

## Metrics

See `docs/results/model_evaluation.json` for the full measured output (per-class
precision/recall/F1, confusion matrix, PR-AUC, healthy false-positive rate, warning lead
time per run, train/validation/test comparison for the overfitting check). Summary
reproduced in `IMPLEMENTATION_STATUS.md`'s Phase 11 section at the time this card was last
updated.

As measured on this training run, only the internal `FAILURE_CLASSIFICATION_BASELINE_V1@1.0.0`
benchmark model reached `VALIDATED` status; `LUBRICATION_ANOMALY_V1@1.0.0` and
`FAILURE_CLASSIFICATION_V1@1.0.0` (the two production-facing model IDs the backend `/ml`
API exposes) remain at `EXPERIMENT`. Since `InferenceService` correctly refuses to serve an
`EXPERIMENT`-status model, and the baseline benchmark is deliberately not one of the
backend's exposed model IDs (it exists only to give the primary classifier a real
comparison floor), the backend `/ml` API's `/latest` endpoint returns
`503 model not available` for both model IDs against this training run — a real, honestly
surfaced consequence of "modest scale," not a bug. The inference mechanism itself was
independently verified end-to-end (real registry lookup, real persisted feature vector,
real `InferenceService` call) against the VALIDATED baseline model directly, confirming the
plumbing works correctly whenever a model does clear the gate — see "Full pipeline
integration result" in the Phase 11 final report / `IMPLEMENTATION_STATUS.md`.

## Known limitations

- **Modest dataset scale.** A bounded number of runs/seeds — real statistical confidence in
  any single metric is limited; treat all numbers as directional evidence of a working
  pipeline, not production-grade validation. Concretely, this scale produced two measured
  outcomes worth stating plainly rather than hiding:
  - `LUBRICATION_ANOMALY_V1` ranks anomalies reasonably well (TEST PR-AUC ≈ 0.84) but its
    VALIDATED promotion gate did not clear on this run — VALIDATION has only one run's worth
    of NORMAL samples to calibrate the operating threshold against, and that threshold then
    produced a higher false-positive rate on TEST (≈0.15) than its 0.05 target allows for
    (gate: ≤2.5x target). The model stays registered at `EXPERIMENT` status, honestly, rather
    than being force-promoted.
  - For `FAILURE_CLASSIFICATION_V1`, the baseline `LogisticRegression` (macro F1 ≈ 0.29 on
    TEST) outperformed the primary `HistGradientBoostingClassifier` (macro F1 ≈ 0.15 on
    TEST) and is the only one of the two that reached `VALIDATED`. This is a real,
    unsurprising finding at ~400 TRAIN rows across 8 classes and ~60 encoded features: a
    heavily regularized linear model generalizes better than a boosted-tree ensemble when
    there are only a few dozen examples per class. `HistGradientBoostingClassifier`'s
    capacity (`max_iter`/`max_depth`) was reduced once from scikit-learn's own defaults after
    an initial run memorized TRAIN outright (see `ml-service/config/classifier_v1.yaml`);
    no further tuning against TEST was performed.
- **Single-label classifier.** `GroundTruthRecord.scenarios` can hold multiple
  simultaneously active faults; the classifier is trained and evaluated against the single
  highest-severity active label per tick. The multi-fault run's evaluation is reported
  honestly as a limitation, not a solved case.
- **`UNKNOWN` bucket is overloaded.** It covers both genuinely low-confidence predictions
  and the two out-of-schema failure modes (`OVER_LUBRICATION`, `LOW_RESERVOIR`) that the
  fixed 8-class label schema does not have a dedicated class for.
- **`NETWORK_FAILURE` is excluded from supervised labels entirely** (a data-quality state,
  not an equipment-failure label) — its samples appear only in anomaly/robustness
  evaluation, never in classifier training/evaluation.
- **No periodic re-training.** Models are trained once per training run and explicitly
  versioned; there is no automatic retraining or promotion loop (ADR-009). Phase 32 added
  an explicit, human-controlled promotion tool (`scripts/promote_model.py`), a model
  comparison tool (`scripts/compare_models.py`), and a reference-scoped (not
  production-grade) drift/coverage check (`ml_service.monitoring.drift`,
  `scripts/check_drift.py`) — see `docs/MLOPS.md`. Neither model ID this card describes
  has been promoted past `EXPERIMENT`, honestly, since neither cleared its promotion gate
  on this dataset.
- **Explainability is heuristic**, not exact Shapley attribution (feature ablation for the
  classifier, train-distribution z-score for the anomaly model) — see
  `docs/ML_ARCHITECTURE.md` "Explainability."
- **Historical eligibility inherits Phase 7's limitation**: point-in-time sensor
  eligibility uses Phase 7's current eligibility state, not a true point-in-time
  eligibility timeline (documented already in `docs/FEATURE_ENGINEERING.md`).

## Expected use

Evidence input to a future Condition Intelligence layer, alongside Phase 9 rule findings —
never a standalone diagnosis. Suitable for demonstrating a credible, real (non-fabricated)
ML pipeline architecture for a synthetic-data reference implementation.

## Prohibited use

- Direct maintenance decisions or work-order generation from model output alone.
- Any production machinery deployment without real sensor validation, real failure-history
  labels, real asset-specific engineering limits, and a functional-safety review (see
  CLAUDE.md "Industrial Adoption Boundary").
- Treating `anomalous=true` as "this machine has failed," or a classifier probability as a
  certainty.

## Human-review boundary

Per CLAUDE.md's three-layer intelligence architecture: this model produces evidence for
Machine & Sensor Intelligence only. Any maintenance action, incident, or work order derived
from this evidence requires Decision Intelligence (asset context, criticality, maintenance
history — not yet implemented) and, per ADR-009/ADR-004, human review before any
operational action.
